# Requirements — ArmoniK .NET Client on native Rust gRPC channel

## Introduction

ArmoniK is a distributed computing platform. Its .NET client (`ArmoniK.Api.Client`) communicates
with the ArmoniK server via gRPC to submit sessions, tasks and retrieve results.

Today, the gRPC transport relies on managed .NET components (`Grpc.Net.Client`,
`WinHttpHandler`, `SocketsHttpHandler`, `GrpcWebHandler`). This choice creates three problems:

1. **Divergent behavior depending on the .NET runtime.** .NET Framework 4.7.2/4.8 uses WinHTTP
   (with a gRPC-Web fallback), while .NET 6+ uses SocketsHttpHandler. Timings, errors and
   capabilities differ silently.
2. **Inoperative options.** `RequestTimeout` and `OverrideTargetName` are declared but have
   no effect (warning only).
3. **Platform limitations.** WinHTTP does not reliably speak HTTP/2 on all targeted Windows
   versions, hence the gRPC-Web fallback.

The project consists of replacing this transport with a **native gRPC channel written in Rust**,
common to all platforms, exposed to .NET via a thin C FFI. The architecture has 5 layers:

```
armonik-transport (Rust, networking)
  → armonik-grpc-channel (Rust, gRPC semantics)
    → armonik-grpc-channel-ffi (Rust → C ABI, runtime isolation)
      → ArmoniK.Api.Client.RustGrpcChannel (C#, native CallInvoker)
        → ArmoniK.Api.Client (C#, gRPC stubs, public API unchanged)
```

The application developer sees no API change. Network behavior becomes identical regardless of
the .NET runtime version. All options become effective.

This document formalizes the V1 requirements for this project, structured by persona.

## Glossary

| Term | Definition |
|------|-----------|
| Channel | Logical resource representing a gRPC connection to an endpoint. Can multiplex multiple HTTP/2 calls. |
| Call | An in-progress gRPC call (request + response), associated with a cardinality (unary, client streaming, server streaming, bidi). |
| CallInvoker | .NET abstraction (`Grpc.Core.CallInvoker`) that allows generated gRPC stubs to emit calls without knowing the transport. |
| Metadata | Key/value pairs transmitted in HTTP/2 headers (request metadata, initial metadata, trailing metadata). |
| Trailing metadata | HTTP/2 headers sent at the end of stream (trailers). On the response side, they contain `grpc-status`, `grpc-message` and user metadata. On the request side, HTTP/2 allows request trailers (sent with `END_STREAM` after the body), but gRPC does not use them in practice — our API does not expose them in V1. |
| end_send | Signal that the client will not send any more messages on this call. Corresponds to `END_STREAM` HTTP/2 on the request body. |
| Deadline | Maximum duration for a call, applied locally and transmitted to the server via the `grpc-timeout` header. |
| Runtime (FFI) | Tokio instance owned by the FFI layer, which executes network tasks and manages the lifecycle (shutdown, quiescence). |
| Quiescence | State in which no task, callback or native thread is in flight. Necessary and sufficient condition for unload. |
| Trampoline | Minimal C callback function that copies a payload and publishes it to a host queue while executing as little code as possible. |
| Host | The calling process (here the .NET runtime) that loads the native library and consumes its events. |
| Consumer token | Identifier chosen by the binding, published in its registry before `call_start`, used to route events. |
| Demand-driven | The client controls the reception rate of messages by explicitly requesting the next ones (`request_messages`). |

## Personas

### ArmoniK application developer

Uses the .NET client to submit sessions, tasks and retrieve results. Responsible for production
deployment and providing observability elements to their ops teams.

### ArmoniK team member

Maintains the `ArmoniK.Api.Client` client, develops the .NET binding (`RustGrpcChannel`),
develops the Rust crates (transport, channel, FFI). Responsible for quality, compatibility and
evolution of the stack.

## Requirement 1: Functional gRPC calls

**User Story:** As an application developer, I want my calls to ArmoniK services (sessions,
tasks, results, events, health) to work correctly via the native channel, so that I do not have
to modify my application code.

### Acceptance Criteria

1. All 4 gRPC cardinalities (unary, client streaming, server streaming, bidirectional streaming)
   are supported, in async mode and in blocking mode (blocking unary via `BlockingUnaryCall`).
2. C# stubs generated by protobuf work without modification with the new `CallInvoker`.
3. Request metadata are transmitted to the server in the HTTP/2 request headers.
4. Response initial metadata (HTTP/2 headers) are accessible to the client.
5. Trailing metadata (HTTP/2 trailers, including `grpc-status` and `grpc-message`) are
   accessible to the client.
6. gRPC messages are correctly framed (length-prefixed) and deframed.
7. The client can send one or more messages and signal the end of sending (`end_send`).
8. The client can receive one or more messages from the response.
9. A unary call returns the result or a gRPC error (non-OK status).
10. A `trailers-only` status (response without body, status in headers) is handled correctly.

---

## Requirement 2: Cancellation and deadline

**User Story:** As an application developer, I want to be able to cancel an in-progress call or
impose a timeout, so that my application is not blocked on a server that is not responding.

### Acceptance Criteria

1. A cancelled `CancellationToken` causes the call to be cancelled (RST_STREAM sent to server).
2. The cancelled call terminates with a `CANCELLED` status.
3. A deadline (configured at channel level or per call) is applied locally.
4. The deadline is transmitted to the server via the `grpc-timeout` header.
5. If the deadline expires before the response, the call terminates with a `DEADLINE_EXCEEDED`
   status.
6. The existing client's `RequestTimeout` option produces an effective deadline (no longer just
   a warning).

---

## Requirement 3: Automatic retry

**User Story:** As an application developer, I want calls that fail on transient errors to be
retried automatically, so that resilience is improved without additional application code.

### Acceptance Criteria

1. Calls that fail with status `UNAVAILABLE`, `ABORTED` or `UNKNOWN` are retried.
2. The default configuration is: 5 total attempts, initial backoff 1s, maximum 5s,
   multiplier 1.5.
3. The retry configuration is configurable.
4. A client streaming call is only retried if the volume of data sent fits within a configurable
   replay buffer. Beyond that, the call is considered committed.
5. A bidirectional call is retryable as long as no response (initial metadata or message) has
   been received AND the replay buffer has not been exceeded.
6. A unary call is retryable as long as the response has not started.
7. The retry respects the global deadline of the call (no retry if the remaining deadline is
   insufficient for the backoff).
8. The total number of attempts includes the initial attempt (5 attempts = 1 initial + 4
   retries).
9. The replay buffer size is configurable (per channel). A buffer of 0 makes streaming calls
   non-retryable as soon as the first message is sent.

---

## Requirement 4: TLS and authentication

**User Story:** As an application developer, I want to be able to connect to an ArmoniK server
secured by TLS with different certificate configurations, so that I can comply with my
infrastructure's security policy.

### Acceptance Criteria

1. The TLS connection uses the system trust roots by default.
2. An explicit PEM CA certificate can be provided by file path to validate the server.
3. mTLS mode is supported with a client certificate provided by path:
   - P12/PFX (with optional password)
   - PEM + separate key
4. mTLS mode also supports resolving the client certificate from the Windows Certificate Store
   (X509Store), identified by Thumbprint, SubjectName or FriendlyName. Resolution is performed
   on the Rust side.
5. Unverified connection mode (insecure) is available via explicit opt-in.
6. The `OverrideTargetName` option effectively modifies the name verified by the TLS handshake.
7. A TLS error produces a diagnosable error message (without exposing secrets: private key paths,
   passwords).

---

## Requirement 5: Proxy

**User Story:** As an application developer, I want the client to respect my environment's proxy
configuration, so that my gRPC calls can traverse enterprise network infrastructures.

### Acceptance Criteria

1. The proxy can be explicitly disabled.
2. An explicit proxy can be configured by URL, with username and password as separate fields.
   If credentials are provided separately, the proxy URI must not contain userinfo
   (user:password in the URL) — this is a configuration error.
3. The proxy can be read from environment variables (`HTTP_PROXY`, `HTTPS_PROXY`, `NO_PROXY`).
4. On Windows, the system proxy (configured in network settings) is readable.
5. Basic proxy authentication is supported.
6. Windows system proxy resolution does not block the calling thread (async with timeout).

---

## Requirement 6: Connection and pool

**User Story:** As an application developer, I want connection management to be transparent and
efficient, so that I do not have to manually manage HTTP/2 connections.

### Acceptance Criteria

1. Channel creation is synchronous and does not perform network I/O by default (lazy
   connection).
2. A configuration option allows an eager connection (HTTP/2 established at channel creation).
   The lazy/eager choice is a configuration option.
3. Multiple concurrent calls are multiplexed on the same HTTP/2 connection.
4. The connection pool manages TCP keepalive and idle timeout.
5. A connect timeout is configurable and applied to connection establishment.
6. A single process can create multiple channels to different endpoints.
7. Channels share a single native runtime (one Tokio thread pool per process).

---

## Requirement 7: Unified cross-runtime behavior

**User Story:** As an application developer, I want my application to have the same network
behavior whether I deploy it on .NET Framework 4.7.2, 4.8, .NET 6 or .NET 8, so that I can
eliminate platform-specific bugs.

### Acceptance Criteria

1. The same application binary (netstandard2.0) produces the same network behavior on .NET
   Framework 4.7.2, 4.8, .NET 6 and .NET 8.
2. Configuration options produce the same effect regardless of the .NET platform.
3. The native transport does not depend on `WinHttpHandler`, `SocketsHttpHandler` or
   `GrpcWebHandler`.
4. Known WinHTTP limitations (no direct HTTP/2 on certain versions) no longer apply.
5. No conditional fallback is needed in application code.

---

## Requirement 8: Packaging and deployment

**User Story:** As an application developer, I want the native channel to be distributed via
NuGet and work without manual configuration, so that I can adopt it with a simple dependency
change.

### Acceptance Criteria

1. The NuGet package contains native binaries for win-x64, win-x86, linux-x64, linux-x86 and
   linux-arm64.
2. The appropriate native binary is resolved automatically at runtime based on the RID.
3. No additional installation (Rust runtime, external DLL) is required.
4. If the native DLL is missing (unsupported RID), channel creation fails with an explicit
   error (no silent fallback).

---

## Requirement 9: API compatibility

**User Story:** As an application developer, I want the switch to the native channel to not
break my existing code, so that I can migrate without development effort.

### Acceptance Criteria

1. The public API of `ArmoniK.Api.Client` does not change (same classes, same methods).
2. Existing configuration options (`GrpcChannel`, endpoint, TLS, proxy, timeout) are preserved
   and mapped to the native channel.
3. The native `CallInvoker` is injectable wherever a `CallInvoker` is expected.
4. Existing usage patterns (DI, factory, configuration via options) are preserved.

---

## Requirement 10: Shutdown and dispose

**User Story:** As an application developer, I want my application's shutdown to be clean and
deterministic, so that I can avoid resource leaks or crashes at shutdown.

### Acceptance Criteria

1. The channel/runtime implements `IAsyncDisposable`.
2. `DisposeAsync` triggers an orderly shutdown: stop accepting new calls, drain in-progress
   calls (or cancel them), wait for quiescence.
3. After dispose, no native thread or callback is in flight.
4. A dispose during active calls cancels them cleanly (CANCELLED status).
5. Unloading the native DLL is safe after dispose (certified by `AK_RELEASED` state).
6. A dispose timeout does not force unload — it leaves the runtime in a non-quiescent state
   rather than risking corruption.

---

## Requirement 11: Diagnostics and errors

**User Story:** As an application developer responsible for production deployment, I want
actionable error messages when the connection fails, so that I can diagnose problems without
reading the transport source code.

### Acceptance Criteria

1. A configuration error (invalid endpoint, certificate not found, unknown option) is reported
   immediately at channel creation with an explicit message.
2. A connection error (DNS, TCP, TLS handshake) is reported with the full cause (cause chain
   flattened into a single UTF-8 message).
3. Error messages do not contain secrets (private key paths, passwords, certificate contents).
4. Error messages do not contain internal debug information (source locations, memory addresses)
   in release builds.
5. Error codes are programmatically distinguishable (configuration vs connection vs transport vs
   timeout vs cancellation).

---

## Requirement 12: Public connector contract (ArmoniK team)

**User Story:** As an ArmoniK team member, I want the public boundary between
`armonik-transport` and `armonik-grpc-channel` to be formalized and stable, so that I can
develop the two crates independently.

### Acceptance Criteria

1. The public connector type/trait is documented with its guarantees and error contract.
2. Configuration options are partitioned according to their semantic owner: transport (endpoint,
   TLS, TCP, proxy, connect timeout) vs channel (retry, deadline, HTTP/2, pool).
3. The connector does not depend on any gRPC notion (no status, no retry, no deadline).
4. The channel does not reinterpret transport options (no double endpoint/TLS resolution).
5. The contract is tested: an incompatible change in the connector breaks an upstream test.
6. The Rust ArmoniK client (`armonik::Client`) uses `armonik-grpc-channel` as its transport
   (via a Tonic adapter or directly), sharing the same gRPC engine that the FFI exposes to
   bindings.

---

## Requirement 13: Stable and versioned ABI (ArmoniK team)

**User Story:** As an ArmoniK team member, I want the C ABI to be versioned and additive, so
that a binding compiled against a previous version continues to work with a newer library.

### Acceptance Criteria

1. `ak_abi_version()` returns the ABI revision.
2. A binding checks the version at load time and diagnoses a mismatch.
3. Additions (new entry points, event kinds, status codes) are additive: an older binding
   ignores what it does not know.
4. No change to the signature, layout, calling convention or semantics of an existing symbol
   within the same major version.
5. Evolvable records use `size` + `version` + `flags` + reserved fields validated to zero.

---

## Requirement 14: Safety and FFI lifecycle (ArmoniK team)

**User Story:** As an ArmoniK team member, I want the FFI layer to guarantee the absence of
memory corruption and a deterministic resource lifecycle, so that I can avoid crashes, leaks and
undefined behavior when used from .NET.

### Acceptance Criteria

1. An invalid handle (already freed, unknown, wrong type) is rejected with an error — never an
   invalid memory access.
2. Data passed from the host to Rust is never read after the downcall returns.
3. Notifications (events) for a call are delivered one at a time (serialized). Notifications
   for different calls may be concurrent.
4. Each accepted call produces exactly one terminal event.
5. No event is delivered after a call's terminal event.
6. After runtime shutdown, no resource creation (channel, call) is accepted.
7. Unloading the native library is only allowed after certified quiescence (`AK_RELEASED`).
8. A panic on the Rust side does not propagate to the host — it is contained and converted to
   an error.

---

## Requirement 15: TLA+ formal model (ArmoniK team)

**User Story:** As an ArmoniK team member, I want a TLA+ model that verifies the safety and
liveness properties of the FFI protocol, so that I can have confidence in the correctness of the
design before implementation.

### Acceptance Criteria

1. The TLA+ models live in `spec/armonik_grpc_ffi/tla/`.
2. The abstract spec (`AbstractGrpc.tla`) describes the observable functional contract (calls,
   terminal, cancel).
3. The FFI spec (`FfiGrpc.tla`) refines the abstract spec by adding concrete mechanisms
   (handles, callbacks, queues, shutdown).
4. The .NET binding spec (`DotNetBinding.tla`) refines the FFI spec by modeling roots, TCS,
   dispose.
5. Safety properties (unique terminal, no late event, no stale dereference) are verified
   without fairness assumptions.
6. Liveness properties (progress toward terminal, progress toward `AK_RELEASED`) are
   conditional on the declared fairness assumptions.
7. Safety properties are proved by TLAPS (TLA+ Proof System) rather than verified by TLC model
   checking. TLC may serve as an exploratory tool but the target is formal proof.

**The automatic retry of Requirement 3 is not modelled**, at any level: no attempt count, no
backoff, no replay buffer, no retryable status codes.  It is a policy over calls the models
already describe rather than a mechanism of the FFI protocol, and it is verified by that
requirement's own tests instead.  The retry the level-2 model does carry is the buffer
lending retry - `BudgetWaitEndsWhenHopeless`, `MessageTooLargeIsNotRetried` - which is the
binding's own scheduling and a different mechanism that shares the word.

## Requirement 16: Comparative performance tests (ArmoniK team)

**User Story:** As an ArmoniK team member, I want a comparative test campaign between the native
transport and the managed transport, so that I can measure the introduced overhead and decide
whether optimizations are needed.

### Acceptance Criteria

1. A benchmark measures unary call latency (P50, P95, P99) with native transport vs managed.
2. A benchmark measures streaming throughput (messages/second) native vs managed.
3. A benchmark measures memory overhead (allocations, RSS) native vs managed.
4. Benchmarks are reproducible in CI (same server, same load, same network).
5. Results are documented and serve as a baseline for future evolutions.
6. The campaign covers at minimum .NET Framework 4.8 and .NET 8.

---

## Requirement 17: Automatic generation of configuration types (ArmoniK team)

**User Story:** As an ArmoniK team member, I want the .NET-side configuration types to be
automatically generated from the Rust types, so that manual maintenance is eliminated and the
risk of drift between the two languages is removed.

### Acceptance Criteria

1. The Rust configuration types (`TransportConfig`, `GrpcChannelConfig`, and their components)
   are the single source of truth for channel options.
2. A JSON schema is automatically generated from these Rust types (via `schemars` or
   equivalent) and committed to the repository.
3. The C# configuration types are automatically generated from this JSON schema.
4. Adding an option on the Rust side automatically propagates to the JSON schema then to the C#
   types without manual intervention.
5. A test verifies that the committed schema is up to date with the Rust types (the build fails
   if the schema is stale).
6. The generated C# types serialize to UTF-8 JSON compatible with Rust `serde::Deserialize`.

## Out of scope for V1

The following items are explicitly excluded from this version:

- OpenTelemetry telemetry (logs, metrics, traces exported from native)
- Hedging
- Generic load balancing and service config
- Configurable gRPC compression
- Generic interceptors
- gRPC-Web
- Bindings Java, Python, C++
- Connectivity state API publique
- Rate limiting public configurable
- Retry policy par method name ou par call (V1 = default channel uniquement ; override par call
  et config par method name sont prévus juste après V1)
