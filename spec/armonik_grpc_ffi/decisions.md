# Decisions

The questions the design had to settle, and what was decided or is still open.

## Open decisions (to be resolved during implementation)

| Question | Options | Impact |
|----------|---------|--------|
| Crate for X509Store Windows | Direct native APIs / `schannel` crate / `windows` crate | Layer 1 |
| Exact handle format | **A monotonic counter per kind, over three disjoint ranges of 64 bits, and no reuse** - the slot map with per-slot generations was reversed on 2026-09-05. A stale handle is refused with a status instead of dereferenced, which is what makes runtime-driven reclamation safe: the host may still hold a token for a call already reclaimed | Layer 3, decided |
| Default replay bytes, per call and per channel | **grpc-dotnet's: 1 MiB per call and 16 MiB per channel**, as `RetryConfig::default` and the `Retry` unit's `CallReplayBytes` and `ChannelReplayBytes` have them. They set how many sent bytes the engine keeps for a replay, which is the one knob between replayability and memory held. Choosable alone: a replay resends what was kept and takes no slot in the send window, so the window does not bound it | T6.3, decided 2026-10-02 |
| Host queue signal mechanism | **Moot: there is no host queue.** The per-call ring replaces it, and its signal wakes the waits taken before a `Set` - never `SemaphoreSlim`, whose `Release` can run a waiter inline on the callback's thread | Layer 4, decided |
| Generator for the C# options | **A build-time tool reading the schema with `Corvus.Json.CodeGeneration`.** A Roslyn generator cannot carry `System.Text.Json`: an analyzer loads inside the compiler, and the documented failure is green under `dotnet build` and red under Visual Studio, which is the one shape no CI can catch. Corvus's own generator has no such problem but emits `readonly struct` readers over a `JsonElement`, which is the wrong shape for a class `IConfiguration` binds and would need a hand-written mutable facade anyway. So its `TypeDeclaration` model does the reading - `$ref`, `$defs`, draft 2020-12 - and this repository decides the C#. The tool runs at build time, so none of Corvus reaches a consumer | Layer 4, decided |
| Connection pool management (idle eviction) | Internal timer vs lazy check | Layer 2 |
| Command delivery to a call actor | Per-actor channel vs atomic flags + notify | Layer 3. Cancel is a flag the actor polls; send and end_send carry data. Reclamation is neither - it is the actor's own step when the debt counters reach zero, so it is a wake rather than a command. A single channel is simpler, two mechanisms are faster |
| Send memory on .NET | **Moot: the host never owns it.** `ak_get_call_buffer` lends native memory, protobuf serializes straight into it, `ak_call_send_message` gives it back. Nothing to pin, nothing to copy, and no managed heap to fragment. One exception, and it is the marshaller's own: `SerializationContext.Complete(byte[])` hands over an array allocated before this binding saw it, and that one is copied in. A ceiling with no room is never answered by allocating - it is backpressure, so the send waits and serializes again | Layer 4, decided |
| Payload allocation shape | One `Vec` per event vs slices of a pooled `Arc<Vec<u8>>` | Layer 3. The ABI already carries `owner` separately from `ptr`, so both fit without changing the contract |
| `ak_channel_release` returns void | Keep void as an idempotent no-op / return `AK_STATUS_HANDLE_STALE` like the other downcalls | Layer 3. The general promise says every downcall on a dead handle reports HANDLE_STALE; the release is the one exception, and either the signature or the promise must move |
| Low-memory probe | Warn when the memory the system has available drops below `ceiling` / no probe | Layer 3. The ceiling bounds what this runtime lends, not what the machine has left; a runtime configured near the machine's limit refuses nothing and is killed instead. Deferred until there is operational data to set a threshold against |
| A ceiling for the receive path | **One count of bytes over what is sent and what is received, with two thresholds, each a field of `ak_runtime_config`.** `memory_ceiling` keeps its meaning, the threshold where work waits: a call stops reading, and a send is refused with `AK_STATUS_BUDGET_BUSY`. A second field beside it is where the engine stops: a decoded message that would pass it ends its call with `RESOURCE_EXHAUSTED`; at 0 it is 1.25 times the first. A release that could make room raises an event on every call refused since the last release - all of them, as waking one needs fairness and loses the wake-up when that call does not try again - with no payload and no delivery credit, as WRITE_DONE takes none. The two `RESOURCE_EXHAUSTED` a call can end with, this one and a message past `Grpc.Receive.MaxMessageSize`, are told apart by their status message only: the code is not one a retry policy names by default. **A send refused for room is served before new reads.** While one waits, the threshold where reads stop is lowered by the largest length waiting, so reception slows only as much as that send needs: the host gives back what it holds, the count falls, and the send then has room. That keeps the promise that a refused send eventually has room, which received bytes in the count would otherwise break under steady traffic. The length and not the charge: a refused charge may exceed the first threshold, while a length past it is `AK_STATUS_MESSAGE_TOO_LARGE`, so the lowered threshold is never below zero. A send waits from its refusal until it is served or its call ends, and the host is obliged to try it again when woken or to cancel the call: one that gives up a send and keeps its call holds reception lowered for the whole runtime, as one that keeps a payload holds its bytes. **A read is two steps, and the decision is the first.** A call is admitted to read its next message against the first threshold, lowered as above; the message is charged when it arrives decoded, where the second threshold applies. Calls admitted together may take the count past the first threshold by a message each, which is accepted: level 1 models the two steps, an atomic read hiding the very overshoot the second threshold bounds | T6.10, decided 2026-10-02 |
| What a replay ceiling means | **The call is committed, and goes on.** One ceiling per call, whatever it sends, so the engine needs no cardinality declared at start. At its own ceiling, or at the channel's total of replay bytes, a call stops being retryable and lets what it kept go; no send is refused for it, and the host sees no new event. As gRFC A6 and grpc-dotnet (`MaxRetryBufferPerCallSize`, `MaxRetryBufferSize`) have it. The runtime's `Ledger` is not the bound: it refuses lends, and what a replay keeps must never refuse a send | T6.1, decided 2026-10-02 |
| Where the transport is chosen | **A selector in `ArmoniK.Api.Client` is acceptable, and `ArmoniK.Api.Common` need not be split.** The native engine and its architectures entering every consumer's build, and the transport carrying Common's message set, are costs accepted. What still holds is that `GrpcChannelFactory.CreateChannel` returns `GrpcChannel`, so it cannot hand back a `NativeChannel` without a breaking change. The selector reads `ArmoniK.Api.Client`'s own configuration, its `GrpcClient` options, and the transport's choice is not a key of the engine's configuration (2026-10-07). The Rust bridge T6.8 waited for is built; the selector's shape is open (tasks.md, T6.8) | T6.8, decided 2026-10-02 and 2026-10-07 |
| Platforms the package promises | **The eleven non-wasm runtime identifiers .NET targets**: win-x64, win-x86, win-arm64, linux-x64, linux-arm, linux-arm64, linux-musl-x64, linux-musl-arm, linux-musl-arm64, osx-x64, osx-arm64. `RustTargets.props` owns the table; the CI matrix, the .NET Framework copy step and the loader derive from it, because four tables that disagree is how an architecture gets built and not packaged. linux-x86 is out - .NET publishes no runtime for it, so nothing could load the asset. musl is in and is not an alias: a shared object linked against glibc does not load on Alpine | Requirement 8.1, decided |
| An error detail channel in the ABI | **`ak_error { kind, ak_bytes detail }` as a nullable out-argument on every fallible entry point, freed by `ak_error_release`.** Nothing is allocated when the host passes NULL, and `detail.owner == NULL` carries a constant message with no allocation at all. The release is a symbol and not a pointer inside the struct: the host would copy a live code pointer into its own memory, and quiescence permits unloading this library. The same change carries requirement 13.5 on the two records the host fills and turns their exact-size check into a minimum - free while the ABI is unpublished, and never free again | Layer 3, decided |
| Splitting `armonik-transport` | **No split, and no feature gate over the engine.** The client compiles sixteen mandatory dependencies where it compiled eight, for an engine it does not use yet - but T7.1 puts it on that engine and T4.1 gives the engine the TLS stack, so both halves converge and the count stops being paid for nothing. A gate would be scaffolding with a demolition date, and a feature position nothing exercises rots | Layer 1, decided |
| Which of `connect.rs` and a new TLS path survives | **`connect.rs::https_connector`, which T4.1 already states.** Its five branches - system roots, an explicit PEM CA, `OverrideTargetName` with its IPv6 case, the insecure opt-in, mTLS from a PEM pair - exist and are tested, so the engine takes the connector rather than growing a second one. The public `TransportConnection` alias changes type with it and costs nothing: no crate here has a publication channel, `publish.yml` carrying jobs for C#, Python, C++, Java and npm and none for cargo | Layer 1, decided |
| How much of `tonic` the engine reuses | **Decided (2026-09-28): the client, on both sides.** A call runs through `tonic::client::Grpc` over the channel's own HTTP/2 session, with a codec that carries the caller's bytes as they are: the length-prefixed framing of what is received, and of what is sent only for a caller's plain `Bytes`, the status in the head and in the trailers, the Trailers-Only shape and the percent-decoding are tonic's. A sent message is not copied: a one-request call's body is swapped below tonic's encoder (call-shapes.md), and a stream's messages are, by T6.13, framed in place in the headroom the engine reserves in front of them, a replay keeping the same buffers - but for small messages ready together, gathered by a copy into one DATA frame as tonic's encoder gathered them. What stays the engine's is what tonic does not do, or does against the gRPC documents, and T9.2 lists each with the test that pins it: the RST_STREAM table, which tonic compiles only under its `server` feature; UNAVAILABLE for a stream a peer's GOAWAY ended, whose reason tonic reads as the stream's; refusing an HTTP answer that is not gRPC before its body is read as messages; UNKNOWN for a message behind a status the head states, where tonic takes that head for Trailers-Only; INTERNAL for trailers that arrive inside a message, where tonic reports their status and drops the partial message; RESOURCE_EXHAUSTED for a message past the limit, where tonic answers OUT_OF_RANGE; removing `grpc-status-details-bin`, which tonic decodes with a panic; and a decoding limit held under what the target can address. A stream that ends with no status is UNKNOWN, as tonic answers it. The session itself - one connection, dial coalescing - is still the channel's, and the metadata type is still this crate's own | Layer 1 |
| How the Rust ArmoniK client reaches the engine | **Through clients generated from the protos that call `GrpcChannel` at the message level, as the FFI does** (decided 2026-10-06, T7.1). A generator reads the descriptor set prost-build writes and emits a client per service over four helpers, prost encoding in place in the frame's headroom; the servers the worker serves stay tonic's. Rejected: tonic's stubs over an adapter that takes HTTP bodies apart into messages, which keeps the stubs and their `GrpcService` generics but implements the framing twice and copies a received message twice; and hand-written clients, which a new RPC would have to remember. The codec is prost's; another is chosen at the generator, as tonic-build's `codec_path` chooses tonic's | Layer 1 |
| How a host configures the engine | **The engine loads it, from the sources the host lists** (decided 2026-10-06, the shape confirmed 2026-10-07, T6.14, `configuration-loading.md`): files in JSON, YAML or TOML, the environment under a prefix, `GrpcClient` by default, read once when the runtime is created, and documents the host writes, a later source over an earlier one. An unknown key is ignored and logged, in every source and on every host (2026-10-07). A binding exposes loads, not its language's configuration framework: the .NET binding takes no `IConfiguration`, so that the engine is the only reader of the files and the environment; the binding parses a command line in .NET's idiom and sends the result as pairs of a key and a text value, read as the environment's are. One document per runtime, the channel defaults within the runtime's options, of which the `armonik` crate's client, having no runtime, takes the endpoint and the channel defaults. A channel loads no source; the runtime does, or a host with no runtime. A file's document is its section named by the prefix, or the whole file when the host asks for no prefix; an environment source with no prefix is refused. A missing file is refused unless marked optional. Both hosts read the runtime's document, `RuntimeOptions` moving to `armonik-transport`, and the endpoint is its `Endpoint`, which `ak_channel_create` takes when given none (2026-10-07) | Layers 1 and 4 |
| The per-call delivery queue on .NET | **Open, and the three objections to `System.Threading.Channels` were wrong.** A bounded `Channel<Slot>` allocates nothing per element that the ring does not, the element being a reference to a native buffer rather than the buffer; a queue that removes the item at the take is no obstacle, because `ak_event_consumed` names the payload it releases, so the engine discharges what comes back rather than what it handed out in order; and level 2's `RingHead`/`RingTail` bind nothing, since that level describes this binding and a refinement needs only a mapping, which may be fictional. What a swap does not touch is the phase machine and the read-versus-token arbiter, which are the actual complexity and have no library answer. What it costs is a package reference on .NET Framework and the release rule: `DeliveryRing.Release()` is the sole releaser of an accepted payload, and a queue that hands the item out cannot hold that invariant - it returns to being the caller's discipline. `DeliveryRing` is one 122-line type, so the swap is mechanical whenever it is wanted | Layer 4 |
| How the C ABI is kept in five places | **Generated from the Rust, and the artefact committed.** `abi.rs`, the header, `NativeMethods.cs`, `tests/layout.rs` and `AbiLayoutTests.cs` are one contract written out five times by hand. `cbindgen` emits the header and `csbindgen` the P/Invoke declarations, verified by the same regenerate-and-compare step `ChannelOptions.g.cs` already has, and the prose the header carries moves into `cbindgen.toml`'s `header` and the Rust doc comments. What does not become redundant is the .NET layout test: `Marshal.SizeOf` and `Marshal.OffsetOf` measure what the CLR does with the declarations, per target framework and per architecture, and a generator proves the declarations match the Rust rather than that the runtime lays them out as Rust does. T3.6, before T4.0 | Layer 3, decided |
| Guarding a buffer or a payload given back twice | **Not built, and if it ever is, behind a feature of its own rather than `cfg(debug_assertions)`.** The `LENT_TAG` in the allocation does not guard this and cannot: it is read from the thing being validated, so a second give-back reads eight bytes of freed memory before any check runs, and no in-allocation scheme fixes that. A guard that works is out of band - a per-call set of live owner pointers, on the lend and the return of every message - and what it would protect is a rule the header already assigns to the host outright, calling a second give-back undefined behaviour rather than a refusal because "there is nothing left to refuse with". The debug build is the wrong home for it twice over: it is the build this repository's own tests run against, so the cost lands on the work rather than on the question, and a guard that exists only where nobody deploys is one no host can ask for when it wants it. A feature flag is the shape - off by default, named, and switched on by whoever is bringing up a host | Layer 3, decided |
| One runtime per process: choice or implementation limit | **A choice, and now requirement 14.9.** Several tokio runtimes in one process share the machine's cores without knowing of each other. `static LIVE` and the three `OnceLock` registries enforce it and the header states it at `ak_runtime_create`; what follows is that the memory ceiling its creator sets is the process's, and a second `NativeRuntime.Create` is refused rather than reconfiguring it | Requirement 14, decided |
| How the engine's threads are laid out | **A thread per channel**, a current-thread tokio runtime that runs the channel's connection and its calls, and a runtime of one worker for the shutdown. A call that stays on one thread pays no wake-up of another: a prototype on the unary benchmark, on .NET 8, was faster at the median in each of three passes against one shared multi-thread runtime, by 26 to 223 us, the low end within the spread between passes. What it costs: a channel's calls share one thread for their CPU work, which nothing yet measures with many calls on one channel; a thread takes about 0.6 ms to start, against 8.5 ms to open a channel over TLS on loopback, and holds a stack and an I/O driver while idle. There is no worker count left to configure, so `worker_threads` leaves `ak_runtime_config` and `WorkerThreads` the runtime's options. A process that opens thousands of channels would want a fixed pool with each channel pinned to one of its threads instead | Requirement 6.7, decided 2026-10-03 |
| The delivery window a channel gets by default | **Four.** With one, the response's message is held until the host has given the head back, a round trip through the host's thread pool between two events that arrive together. On the .NET 8 unary benchmark, in four interleaved passes, two credits took that step from 38-49 us to 12-14 us at the median and the end of a call from 128-150 us to 93-131 us; four, measured in a pass of their own, did as well. A unary call needs two, its head and its message; past that each credit is a message of a stream delivered without waiting for the host to give the one before back. That is reasoned rather than measured: on the streaming benchmark, on a loaded machine, neither two nor four separated from one beyond the spread between four interleaved passes (75-212 MiB/s with one, 86-122 with two, 94-113 with four). Exempting the head from the window instead did as well for a unary call in the same four passes (7-20 us for the step, 101-135 us for the end of a call), at the cost of a ring slot in the binding and a change to the model. A call that asks for nothing holds at most four payloads and its terminal, in a ring of eight slots on the .NET side | Requirement 16, decided 2026-10-03 |
| When a connection writes | **Once the work already ready adds nothing to the write, or it holds `Http2.Send.CoalescingBytes`, 16 KiB by default.** hyper writes what its HTTP/2 connection has buffered each time that task is polled, and a request's message, handed over from the host's thread while its headers wait, came after that poll: every unary call made two writes on its socket, the headers and then the message. A write waits a round of the runtime while the round adds bytes to it. On the .NET 8 unary benchmark, in four interleaved passes, 97 to 99 % of calls made one write instead of two, the server read 99.6 % of requests in one read, and the time from the start of a call to its send's acquittal fell from 94-120 us to 58-84 us, from 184-192 us to 81-86 us with the pool busy. The call's P50 moved within the spread idle and fell from 640-678 us to 601-619 us busy; a write cost 35 us on that machine at rest and 60 to 110 us loaded, which is what the saving scales with. Rejected: serving the tasks woken from another thread first (`global_queue_interval(1)`), under which a host sending without pause starves the connection's own task; and holding a write for a time, which tokio's millisecond timer cannot measure in microseconds | Requirement 16, decided 2026-10-03 |
| When a response reaches the host | **Once the work already ready reads nothing more of it, or the delivery holds `Grpc.Host.Receive.CoalescingBytes`, 16 KiB by default** - the writes' rule, on the way in. The connection and the call share the channel's thread, so a read that finds the response's next part not yet decoded is not a part that has not arrived: the connection decodes it on its next turn. Delivered at once, a unary answer that Kestrel writes in parts reached the host as a head alone and then the message with its status: two callbacks, and two wake-ups of a reader that waits for the whole response. Measured on .NET 11 with timestamps at each step of 10 000 unary calls, every answer now comes in one callback, and the time from the response head to the caller's continuation fell by about 13 us idle and 4 us busy; the call's latency moved within the machine's spread. Rejected: holding the head until the message, which would delay the headers of a call whose message comes late | Requirement 16, decided 2026-10-04 |
| Where a call is reclaimed | **On the thread that clears its last debt** - the host's, inside the downcall that gives the last payload or buffer back, or the engine's, as the last callback returns - which removes it from the table once, under a flag. Reclaiming is a table removal; a task waiting for the debt had to be woken on the channel's thread for it, and the host's downcall paid the wake-up. Measured on .NET 11 with timestamps in the engine, `ak_events_consumed` for a unary answer fell from 17 to 10.5 us, idle and busy alike, the wake-up from about 10 us to under 1, and the channel's thread is no longer woken at the end of a call. Rejected: the call's task waiting for the debt | Requirement 16, decided 2026-10-04 |
| How options that exclude one another are spelled | **As one Rust enum, which the schema renders as a `oneOf` of objects of one key, and C# as a closed hierarchy of records** - how the server is verified (`CaPem`, `CaStore`, `Unverified`), who the client is (`Pem`, `P12`, `Store`), the proxy (`None`, `System`, `Url`, `UrlWithCredentials`), how a store finds its certificate (`Thumbprint`, `SubjectName`, `FriendlyName`) and the receive windows (`Fixed`, `Adaptive`). The key names the alternative and holds what it carries, `true` for nothing, so a document naming two is refused as it is read, by serde, and no reader checks pairs of keys. A C# choice is an abstract record with a private constructor and sealed records nested in it, positional, consumed by pattern matching; netstandard2.0 takes `IsExternalInit` from its package. The schema lists properties as the Rust type declares them (schemars' `preserve_order`), which is the order a record takes its parameters in. Rejected: the flat keys side by side (`CaCertPath`, `AllowUnsafeConnection`, `CertPem` in one object), as `GrpcClient` spells them, which the reader refused in pairs and a merge of two documents could combine into one neither stated | T3.3, decided 2026-10-05 |
| How a channel's options are grouped | **By the layer each acts on: `Transport` the dial and the socket (`ConnectEagerly` among them), `Http2` the session, `Grpc` the calls - `UserAgent`, `DefaultDeadlineSeconds`, `Retry` - and under `Grpc.Host` what crosses between the host and the engine; and within a layer, what it sends under `Send` and what it receives under `Receive`, one name for the same thing either way: `Http2.Send.CoalescingBytes` and `Http2.Send.StreamBufferSize`, `Http2.Receive`'s windows, fixed or adaptive, `Grpc.Send.MaxMessageSize` and `Grpc.Receive.MaxMessageSize`, `Grpc.Host.Send.Window` and `Grpc.Host.Receive.Window` and `Receive.CoalescingBytes`.** `UserAgent` is gRPC's, as the gRPC over HTTP/2 specification defines it. The two coalescings are a layer apart: `Http2.Send.CoalescingBytes` gathers the frames of every call into the socket's writes, `Grpc.Host.Receive.CoalescingBytes` one call's delivery to the host. Rejected: options of every layer side by side at the top of the document | T3.3, decided 2026-10-05 |
| How a session sizes what its peer may send | **As an alternative of `Http2.Receive`: `Fixed`, two windows announced as the session opens, 2 MiB per call and 5 MiB for the connection by default, or `Adaptive`, hyper's flow control, whose windows start at 65535 and grow with the bandwidth-delay product its PINGs measure, up to 16 MiB.** hyper's adaptive windows replace the two sizes rather than start from them, so the two exclude one another and are an enum. `Fixed` stays the default: on a link whose bandwidth-delay product fits in 2 MiB, adaptive windows only start slower. A channel that states no `Receive` keeps its defaults' alternative, as it keeps their proxy. Rejected: patching hyper so that its adaptive windows start at the fixed sizes, a patch of hyper to carry for a start that only a distant link would see | T3.3, decided 2026-10-05 |
| How a message past the send limit ends | **Its call ends `RESOURCE_EXHAUSTED`, as the gRPC status table has a message past the configured limit end, and none of it is sent.** A stream's message is refused at the send that gives it, before the queue, so the caller hears it there too; a one-request call is checked before anything is dialled. Through the ABI the send is accepted and acquitted like any other, and the terminal reports the refusal. `Grpc.Send.MaxMessageSize` has no default, as grpc-dotnet's `MaxSendMessageSize` has none. Rejected: ending it `CANCELLED`, the code a stop on this side otherwise earns, which says nothing of why | T3.3, decided 2026-10-05 |
| What a commit says of the buffer | **How many bytes the host wrote: `ak_call_send_message(handle, buf, written)`, and only those are sent.** So the arena is not zeroed, nothing past `written` is ever read, and a lend may be the most a message will take rather than its exact size. A commit of more than the lend, or a write past its end that changes the sentinel of eight bytes after every lend, which the commit and `ak_return_call_buffer` check, is `AK_STATUS_CORRUPTED`; a write that leaves the sentinel as it was goes unseen. Either overrun takes the buffer back without freeing it, since what was overwritten may be the allocator's own record, and shuts the runtime down. Rejected: zeroing every lend and sending it whole, which costs a pass over each buffer and sends what a host that wrote less left there | T3.3, decided 2026-10-05 |
| Where a send's arena goes once it is sent | **Back to its channel, which lends it again to a lend it fits, within an eighth, for arenas of 64 KiB and more.** A large allocation freed goes back to the system and the next one faults every page in again. On the POC branch under glibc's default allocator, a ring of six spare 4 MiB encode buffers took a framed 16 MiB upload at eight streams in flight from 10.62 to 9.53 ms, and changed nothing under a pinned allocator; the faults are what tonic's own fresh encode buffer cost there, 1200 to 2200 minor ones per 16 MiB call. The spares are counted under the ceiling beside the host's charges, not in `bytes_used`, and any charge that would take the two past it empties them first, so they never refuse a lend or hold a read. A lend that takes a spare is charged its slack, at most an eighth, beside its request, or allocates when the ceiling has no room for it. A channel keeps four per buffer a call may have out, the oldest given up for the newest, until it closes or a charge needs their room. Near the ceiling, where a charge and the spares do not fit together, the spares go first and nothing is lent again. Smaller arenas are freed, since the allocator serves them from memory it holds. Rejected: a pool per call, which a call of one request never reuses; a pool per runtime, where the user chose the channel | T3.3, decided 2026-10-05 |
| How DATA frames reach the socket | **In fewer, larger writes, with h2-batch's patch of h2 0.4.19 and as many frames of the peer's largest size per queued part as `Http2.Send.FramesPerWrite` says, per connection.** The patch is hyperium/h2#903, several DATA frames per vectored write, with what the POC branch added to it, a queued part spanning several frames, and the count made the connection's, set through `h2::with_frames_per_write` around the handshake. Measured here, a 4 MiB request over loopback goes out in 17 writes at 16 frames against 257 at 1. Only the patch is in the repository: `packages/rust/patches/h2-batch/build.sh` takes h2 from cargo's cache of crates.io, checks it against Cargo.lock, patches a copy in the target directory and builds against it for that run alone, and the .NET binding does so when `NativeEngineH2Batch` is `true`. Every other build is stock h2, and refuses more than one frame per write. Above one, a reset call may send up to that many frames less one before its RST_STREAM, which is why 1 stays the default. At any count, the patched build differs from stock h2: a control frame waits behind the DATA already queued, up to one part per active stream, where stock h2 holds one frame. Rejected: a vendored copy of h2, which would carry all of h2 to change six files; a fork, which the build would have to fetch; the POC's `AK_H2_COALESCE` environment variable, which is one value for the process | T3.3, decided 2026-10-05 |
| How many calls a connection carries | **As many as `Http2.SimultaneousCallsPerConnection` says and its server allows, the channel opening as many connections as its calls in flight need; unset, as many as the server allows.** The server's bound is the SETTINGS_MAX_CONCURRENT_STREAMS it sends, read from the connection each time a call looks for one: a call past it would wait inside h2 for another to end, which behind nginx's `http2_max_concurrent_streams` blocks a long-lived call for good where grpc-dotnet opens a second connection. Until the server's SETTINGS arrive, h2 assumes 100, so the calls placed on a new connection first may go past a lower bound, which neither nginx's default of 128 nor Kestrel's of 100 is. The server refuses those it sees: a refused call whose request is still held whole, as a unary one's is, goes again once, where there is room, and one that has sent more than it holds, or is refused again, ends UNAVAILABLE, for its retry policy to take. A server that allows no stream for now has calls wait in h2, the channel dialling no more for them. One h2 has not sent when the bound arrives waits for a stream of that connection to end. Behind nginx, a client that resets too many streams is answered with GOAWAY ENHANCE_YOUR_CALM, which ends every call on that connection; at 1 call per connection it ends one. The connections are a pool below the ABI, invisible to the host and to the formal model: a call takes the fullest that has room, then the one idle most recently, so that the others go idle and close on their own idle timeout when `Http2.IdleTimeoutSeconds` is set; if no connection has room, it joins a dial in flight that has room, or starts one. A call counts on its connection from its dispatch to the end of its response and of its request: a call whose response ends first keeps its request open, and its stream, until the engine half-closes it, and the next call would otherwise overlap it.
