# Decisions

The questions the design had to settle, and what was decided or is still open.

## Open decisions (to be resolved during implementation)

| Question | Options | Impact |
|----------|---------|--------|
| Crate for X509Store Windows | Direct native APIs / `schannel` crate / `windows` crate | Layer 1 |
| Exact handle format | **A monotonic counter per kind, over three disjoint ranges of 64 bits, and no reuse** - the slot map with per-slot generations was reversed on 2026-09-05. A stale handle is refused with a status instead of dereferenced, which is what makes runtime-driven reclamation safe: the host may still hold a token for a call already reclaimed | Layer 3, decided |
| Default replay bytes, per call and per channel | **grpc-dotnet's: 1 MiB per call and 16 MiB per channel**, as `RetryConfig::default` and the `Retry` unit's `CallReplayBytes` and `ChannelReplayBytes` have them. They set how many sent bytes the engine keeps for a replay, which is the one knob between replayability and memory held. Choosable alone: a replay resends what was kept and takes no slot in the send window, so the window does not bound it | T6.3, decided 2026-10-02 |
| Host queue signal mechanism | **Moot: there is no host queue.** The per-call ring replaces it, and its signal wakes the waits taken before a `Set` - never `SemaphoreSlim`, whose `Release` can run a waiter inline on the callback's thread | Layer 4, decided |
| Generator for the C# options | **A build-time tool reading the schema with `Corvus.Json.CodeGeneration`.** A Roslyn generator cannot carry `System.Text.Json`: an analyzer loads inside the compiler, and the documented failure is green under `dotnet build` and red under Visual Studio, which is the one shape no CI can catch. Corvus's own generator has no such problem but emits `readonly struct` readers over a `JsonElement`, which is the wrong shape for a class `IConfiguration` binds and would need a hand-written mutable facade anyway. So its `TypeDeclaration` model does the reading - `$ref`, `$defs`, draft 2020-12 - and this repository decides the C#. The tool runs at build time, so none of Corvus reaches a consumer | Layer 4, decided |
| Connection pool management (idle eviction) | Internal timer vs lazy check | Layer 2 |
| Command delivery to a call actor | Per-actor channel vs atomic flags + notify | Layer 3. Cancel is a flag the actor polls; send and end_send carry data. Reclamation is neither - it is the actor's own step when the debt counters reach zero, so it is a wake rather than a command. A single channel is simpler, two mechanisms are faster |
| Send memory on .NET | **Moot: the host never owns it.** `ak_get_call_buffer` lends native memory, protobuf serializes straight into it, `ak_call_send_message` gives it back. Nothing to pin, nothing to copy, and no managed heap to fragment. One exception, and it is the marshaller's own: `SerializationContext.Complete(byte[])` hands over an array allocated before this binding saw it, and that one is copied in. A ceiling with no room is never answered by allocating - it is backpressure, so the send waits and serializes again | Layer 4, decided |
| Payload allocation shape | One `Vec` per event vs slices of a pooled `Arc<Vec<u8>>` | Layer 3. The ABI already carries `owner` separately from `ptr`, so both fit without changing the contract |
| `ak_channel_release` returns void | Keep void as an idempotent no-op / return `AK_STATUS_HANDLE_STALE` like the other downcalls | Layer 3. The general promise says every downcall on a dead handle reports HANDLE_STALE; the release is the one exception, and either the signature or the promise must move |
| Low-memory probe | Warn when the memory the system has available drops below `ceiling` / no probe | Layer 3. The ceiling bounds what this runtime lends, not what the machine has left; a runtime configured near the machine's limit refuses nothing and is killed instead. Deferred until there is operational data to set a threshold against |
| A ceiling for the receive path | **One count of bytes over what is sent and what is received, with two thresholds, each a field of `ak_runtime_config`.** `memory_ceiling` keeps its meaning, the threshold where work waits: a call stops reading, and a send is refused with `AK_STATUS_BUDGET_BUSY`. A second field beside it is where the engine stops: a decoded message that would pass it ends its call with `RESOURCE_EXHAUSTED`; at 0 it is 1.25 times the first. A release that could make room raises an event on every call refused since the last release - all of them, as waking one needs fairness and loses the wake-up when that call does not try again - with no payload and no delivery credit, as WRITE_DONE takes none. The two `RESOURCE_EXHAUSTED` a call can end with, this one and a message past `Grpc.Receive.MaxMessageSize`, are told apart by their status message only: the code is not one a retry policy names by default. **A send refused for room is served before new reads.** While one waits, the threshold where reads stop is lowered by the largest length waiting, so reception slows only as much as that send needs: the host gives back what it holds, the count falls, and the send then has room. That keeps the promise that a refused send eventually has room, which received bytes in the count would otherwise break under steady traffic. The length and not the charge: a refused charge may exceed the first threshold, while a length past it is `AK_STATUS_MESSAGE_TOO_LARGE`, so the lowered threshold is never below zero. A send waits from its refusal until it is served or its call ends, and the host is obliged to try it again when woken or to cancel the call: one that gives up a send and keeps its call holds reception lowered for the whole runtime, as one that keeps a payload holds its bytes. **A read is two steps, and the decision is the first.** A call is admitted to read its next message against the first threshold, lowered as above; the message is charged when it arrives decoded, where the second threshold applies. Calls admitted together may take the count past the first threshold by a message each, which is accepted: level 1 models the two steps, an atomic read hiding the very overshoot the second threshold bounds | T6.10, decided 2026-10-02 |
| What a replay ceiling means | **The call is committed, and goes on.** One ceiling per call, whatever it sends, so the engine needs no cardinality declared at start. At its own ceiling, or at the channel's total of replay bytes, a call stops being retryable and lets what it kept go; no send is refused for it, and the host sees no new event. As gRFC A6 and grpc-dotnet (`MaxRetryBufferPerCallSize`, `MaxRetryBufferSize`) have it. The runtime's `Ledger` is not the bound: it refuses lends, and what a replay keeps must never refuse a send | T6.1, decided 2026-10-02 |
| Where the transport is chosen | **A selector in `ArmoniK.Api.Client` is acceptable, and `ArmoniK.Api.Common` need not be split.** The native engine and its architectures entering every consumer's build, and the transport carrying Common's message set, are costs accepted. What still holds is that `GrpcChannelFactory.CreateChannel` returns `GrpcChannel`, so it cannot hand back a `NativeChannel` without a breaking change. The selector reads `ArmoniK.Api.Client`'s own configuration, its `GrpcClient` options, and the transport's choice is not a key of the engine's configuration (2026-10-07). Decided on 2026-10-07 and built by T6.8: a `Transport` option in `GrpcClient`, `Managed` (the default, grpc-dotnet, unchanged) or `Native`, and not a value of `HttpMessageHandler`; `GrpcChannelFactory.CreateChannel` keeps returning `GrpcChannel`, with a new `CreateChannelBase` that returns a `ChannelBase` and honours `Transport`. A `Transport` of `Native` given to `CreateChannel` is logged as not honoured, as `OverrideTargetName` is, and the managed channel is made | T6.8, decided 2026-10-02 and 2026-10-07 |
| How an option is turned off | **By a value of 0 where "none" is a state of the option and not only its default** (decided 2026-10-07, T6.8's follow-up). A source that leaves an option out leaves what an earlier source set, so an absent key is the default or the earlier value, and a source that wants none has to say so; saying nothing could not tell "keep" from "none", which is why a `GrpcClient` with an infinite `KeepAliveTime` could not turn off the keepalive the floor sets. Zero is the one spelling every source has, a number being all an environment variable, a command line and a file's scalar carry, where a `null` would not survive the text sources and the generated C# types, whose options are nullable and cannot tell a key left out from a key set to null. **Changed, and a value above zero keeps its own bound** (a value between 0 and the least is still refused): `Transport.TcpKeepalive.IdleSeconds` (0 is no keepalive, and `IntervalSeconds` and `Retries` are then not read, instead of refused for want of an idle time), `Http2.KeepAliveIntervalSeconds` (no PINGs), `Http2.IdleTimeoutSeconds` (a connection is never closed for being idle), `Grpc.DefaultDeadlineSeconds` (a call has no deadline of the channel's), `Grpc.RateLimit.Calls` (no limit, `PerSeconds` not read). **Left**, each for its reason: `Transport.ConnectTimeoutSeconds` (default 60; a zero timeout reads as expiring at once, and the operating system bounds a dial that has none), `Http2.KeepAliveTimeoutSeconds` (no timeout would make a PING that never fails; it matters only beside an interval), `TcpKeepalive.IntervalSeconds` and `Retries` (the operating system's value is their absence), `Grpc.Send.MaxMessageSize`, `Grpc.Receive.MaxMessageSize`, `Http2.Send.MaxHeaderListSize` and `Http2.SimultaneousCallsPerConnection` (caps, whose "no limit" is stated by the largest value, and for which zero is refused as it admits nothing), `Grpc.Retry.MaxAttempts` (1 is no retry), the replay bytes and `Http2.Send.CoalescingBytes` (0 is already a value of its own: nothing kept, nothing gathered), the windows and buffers (sizes with no "none"), `ConnectEagerly` and `KeepAliveWhileIdle` (booleans, false is off), `Transport.Proxy` (its `None` alternative), `Grpc.Send.Compression` (an encoding with no `identity` variant: a later source cannot unset one, a gap noted and left), `Grpc.Receive.Compression` (a list, which `[]` from a file or a document turns off, a stated list replacing the earlier one whole; a text source cannot state a list), the TLS options (alternatives with none to state). The schema states the minimum as 0 for the five, where the engine's own least above zero is in the option's description, so the generated C# `Validate` admits a value the engine then refuses when the channel is created. `GrpcClient` sends 0 for a `KeepAliveTime`, a `MaxIdleTime` or a `RequestTimeout` that is zero, negative or infinite, and states it only when it is set (see "What a GrpcClient sets") | Layers 1 and 4 |
| What a GrpcClient sets | **What the caller set, even to the default; an option left alone is the engine's sources' to decide** (decided 2026-10-08, T6.8's follow-up). "Differs from the default" was the wrong test: a caller who writes `MaxAttempts = 5` over an environment that says 3 means 5, and one who never mentions it means the environment. `GrpcClient` therefore records which of the options the native transport reads (the 17 from `AllowUnsafeConnection` to `ProxyPassword`) were assigned: each is a property over a field that keeps its default, with a setter that notes the name, the public API and the managed transport unchanged. `Endpoint`, `Transport`, `HttpMessageHandler` and `ReusePorts` are not recorded, the translator not needing them. A configuration binder reads each property and, when the key is absent, assigns it what it read, (measured with Microsoft.Extensions.Configuration.Binder 6.0, 7.0, 8.0, 9.0 and 10.0): an assignment of the value just read is therefore not a choice, and is not recorded, which means an explicit assignment of a property's value right after reading it is not recorded either, though it should override an engine source holding another value; the library's own reads of the options (the translator's) count, so the last option read stays in that case until another is read or assigned. Binding from an `IConfiguration` (the Options pattern) then records exactly the keys the configuration holds, one set to its default included, with the binders of 7.0 and later; the binder 6.0 reads a property before assigning every key, present or not, so a key present at the property's default is not recorded there, and a different value is. The options are not synchronised, as a type of options is not. An option with no neutral value to send (the TLS verification, the certificates, the target name) sends nothing when set to its empty or false value, and an empty `Proxy` sends the system's, the managed default. The runtime's defaults translate every option, whatever was set; the backoff pair rule applies to the options that are set. Rejected: comparing with the default, which cannot tell the two; a nullable property, which breaks the source-compatibility of the existing callers that read an `int`; wrapper types for the options, which change what `var x = options.MaxAttempts` is | T6.8 |
| Who owns the native runtime of a process, and what feeds it | **`NativeChannelFactory.Instance`, a static singleton in `ArmoniK.Api.Client`, which starts the runtime with its first channel and keeps it until `ShutdownAsync`** (decided 2026-10-07, T6.8). One runtime per process is the engine's rule, so the owner is the process's. The engine's own option types are not an `IConfiguration`, so `ArmoniK.Api.Client` cannot bind them from the environment; it hands the engine three sources, a later one over an earlier one: the defaults of `GrpcClient` translated as an object (`LoadConfigFromObject`), the environment under `ArmoniK__Client__Grpc__` (`LoadConfigFromEnvironment`, read by the engine), and its command line (`LoadConfigFromCommandLine`, the process's own arguments unless the caller gives some). `ArmoniK__Client__` is the family of the client's configuration and `Grpc` the part the engine reads; the managed options stay in their `GrpcClient` section. Each channel then states, as its own options, what its `GrpcClient` sets (see "What a GrpcClient sets"), so a certificate or a proxy may differ from one channel to the next, an option a `GrpcClient` leaves alone is the engine's sources' to decide, and one it sets wins. A keepalive, an idle time or a request timeout that is zero or infinite is sent as 0, which the engine reads as none (see "How an option is turned off"), so it turns off what the floor or the environment set. A value outside the engine's bounds (a keepalive under a second) is refused as `ArgumentOutOfRangeException` when the channel is opened. `OverrideTargetName` is applied whenever it is set, where the managed transport ignores it, but no TLS option is sent for an `http://` endpoint, which the managed transport ignores and the engine refuses (an empty `Endpoint` being the engine's, its scheme unknown, they are sent). Each backoff is sent when it is stated, and the one that is not is sent too when the stated one would pass it, since the engine refuses a maximum below the initial one: a maximum below the initial one is raised to it, and an initial one above a stated maximum is lowered to it (grpc-dotnet draws its first delay up to the initial backoff and caps the later ones at the maximum, where two stated bounds that cross are sent with the maximum raised). The bound that is not set is compared with its default in `GrpcClient`, not with the value the environment gives the engine, which the translator cannot see: a set initial backoff over a smaller maximum from the environment replaces that maximum. A channel is refused while the engine is shutting down, and the command line is read when the engine starts, a later one being logged and ignored. An empty `Endpoint` is the runtime's `Endpoint`. `HttpMessageHandler` and `ReusePorts` are not read, `HttpMessageHandler` logged. A command line the provider refuses (`-x=1`) is logged and skipped when it is the process's own and refused when the caller gave it. Rejected: one runtime per `GrpcClient`, which the engine forbids; binding the engine's options from the caller's `IConfiguration`, which T6.14 settled against | T6.8 |
| Platforms the package promises | **The eleven non-wasm runtime identifiers .NET targets**: win-x64, win-x86, win-arm64, linux-x64, linux-arm, linux-arm64, linux-musl-x64, linux-musl-arm, linux-musl-arm64, osx-x64, osx-arm64. `RustTargets.props` owns the table; the CI matrix, the .NET Framework copy step and the loader derive from it, because four tables that disagree is how an architecture gets built and not packaged. linux-x86 is out - .NET publishes no runtime for it, so nothing could load the asset. musl is in and is not an alias: a shared object linked against glibc does not load on Alpine | Requirement 8.1, decided |
| An error detail channel in the ABI | **`ak_error { kind, ak_bytes detail }` as a nullable out-argument on every fallible entry point, freed by `ak_error_release`.** Nothing is allocated when the host passes NULL, and `detail.owner == NULL` carries a constant message with no allocation at all. The release is a symbol and not a pointer inside the struct: the host would copy a live code pointer into its own memory, and quiescence permits unloading this library. The same change carries requirement 13.5 on the two records the host fills and turns their exact-size check into a minimum - free while the ABI is unpublished, and never free again | Layer 3, decided |
| Splitting `armonik-transport` | **No split, and no feature gate over the engine.** The client compiles sixteen mandatory dependencies where it compiled eight, for an engine it does not use yet - but T7.1 puts it on that engine and T4.1 gives the engine the TLS stack, so both halves converge and the count stops being paid for nothing. A gate would be scaffolding with a demolition date, and a feature position nothing exercises rots | Layer 1, decided |
| Which of `connect.rs` and a new TLS path survives | **`connect.rs::https_connector`, which T4.1 already states.** Its five branches - system roots, an explicit PEM CA, `OverrideTargetName` with its IPv6 case, the insecure opt-in, mTLS from a PEM pair - exist and are tested, so the engine takes the connector rather than growing a second one. The public `TransportConnection` alias changes type with it and costs nothing: no crate here has a publication channel, `publish.yml` carrying jobs for C#, Python, C++, Java and npm and none for cargo | Layer 1, decided |
| How much of `tonic` the engine reuses | **Decided (2026-09-28): the client, on both sides.** A call runs through `tonic::client::Grpc` over the channel's own HTTP/2 session, with a codec that carries the caller's bytes as they are: the length-prefixed framing of what is received, and of what is sent only for a caller's plain `Bytes`, the status in the head and in the trailers, the Trailers-Only shape and the percent-decoding are tonic's. A sent message is not copied: a one-request call's body is swapped below tonic's encoder (call-shapes.md), and a stream's messages are, by T6.13, framed in place in the headroom the engine reserves in front of them, a replay keeping the same buffers - but for small messages ready together, gathered by a copy into one DATA frame as tonic's encoder gathered them. What stays the engine's is what tonic does not do, or does against the gRPC documents, and T9.2 lists each with the test that pins it: the RST_STREAM table, which tonic compiles only under its `server` feature; UNAVAILABLE for a stream a peer's GOAWAY ended, whose reason tonic reads as the stream's; refusing an HTTP answer that is not gRPC before its body is read as messages; UNKNOWN for a message behind a status the head states, where tonic takes that head for Trailers-Only; INTERNAL for trailers that arrive inside a message, where tonic reports their status and drops the partial message; RESOURCE_EXHAUSTED for a message past the limit, where tonic answers OUT_OF_RANGE; removing `grpc-status-details-bin`, which tonic decodes with a panic; and a decoding limit held under what the target can address. A stream that ends with no status is UNKNOWN, as tonic answers it. The session itself - one connection, dial coalescing - is still the channel's, and the metadata type is still this crate's own | Layer 1 |
| How the Rust ArmoniK client reaches the engine | **Through clients generated from the protos that call `GrpcChannel` at the message level, as the FFI does** (decided 2026-10-06, T7.1). A generator reads the descriptor set prost-build writes and emits a client per service over four helpers, prost encoding in place in the frame's headroom; the servers the worker serves stay tonic's. Rejected: tonic's stubs over an adapter that takes HTTP bodies apart into messages, which keeps the stubs and their `GrpcService` generics but implements the framing twice and copies a received message twice; and hand-written clients, which a new RPC would have to remember. The codec is prost's; another is chosen at the generator, as tonic-build's `codec_path` chooses tonic's | Layer 1 |
| How a host configures the engine | **The engine loads it, from the sources the host lists** (decided 2026-10-06, the shape confirmed 2026-10-07, T6.14, `configuration-loading.md`): files in JSON, YAML or TOML, the environment under a prefix, `ArmoniK__Client__Grpc` by default (2026-10-07: `ArmoniK__Client__` is the ArmoniK client's family and `Grpc` the part this engine reads; a prefix is a path, its parts the nested sections of a file), read once when the runtime is created, and documents the host writes, a later source over an earlier one. An unknown key is ignored and logged, in every source and on every host (2026-10-07). A binding exposes loads, not its language's configuration framework: the .NET binding takes no `IConfiguration`, so that the engine is the only reader of the files and the environment; the binding parses a command line in .NET's idiom and sends the result as pairs of a key and a text value, read as the environment's are. One document per runtime, the channel defaults within the runtime's options, of which the `armonik` crate's client, having no runtime, takes the endpoint and the channel defaults. A channel loads no source; the runtime does, or a host with no runtime. A file's document is its section named by the prefix, or the whole file when the host asks for no prefix; an environment source with no prefix is refused. A missing file is refused unless marked optional. Both hosts read the runtime's document, `RuntimeOptions` moving to `armonik-transport`, and the endpoint is its `Endpoint`, which `ak_channel_create` takes when given none (2026-10-07) | Layers 1 and 4 |
| What a host sees of the engine | **Its logs and effective configuration, its metrics, its traces, as `observability.md` records** (decided 2026-10-07, T10.1 to T10.3). Each stream of events has a callback of its own, given when the runtime is created and never replaced - the log callback is two fields of `ak_runtime_config` and `ak_config`, and the trace callback is decided to be given the same way - under the runtime callback's thread contract; one process-wide dispatcher routes the engine's events to the runtime there is, and the engine filters the logs and samples the spans. The metrics, counters and gauges, are read on demand, `ak_runtime_stats`, rather than pushed through a callback, which would cost a crossing per measurement: a .NET `Meter`'s observable instruments read them at their collector's pace. Histograms are set aside. Which spans are built is configured, none while no trace callback is given. The effective configuration is logged, every value but the secrets. A call's trace context is a field of `ak_call_start_options`. A queue the host drains would be preferable to a log callback, but is hard to make generic across languages, so the callback is what the ABI carries | Layers 1, 3 and 4 |
| How the log filter matches a target | **By module-path segment, and by text only where the target ends in `*`** (decided 2026-10-07, T10.1). `h2=warn` covers `h2` and `h2::proto`, not `h2x`; `armonik_transport=debug` covers `armonik_transport::grpc` and not `armonik_transport_ffi`; `armonik_transport*=debug` covers both, and `*=debug` every target (confirmed 2026-10-07, with the default below). The filter is given through the runtime's options alone, `Logging.Filter`: `ak_runtime_config` has no field for it, so a runtime created from it logs by the default. The most specific directive decides. The engine has its own matcher, since `tracing-subscriber`'s `Targets` and `EnvFilter` match by text prefix. The default is `*=warn,armonik_transport*=info` (decided 2026-10-08): only the engine's own targets are raised, so no dependency is listed and a new one is quiet. A filter the user gives replaces the default whole, and a target none of its directives covers is off, and a level for every target, as `*=warn` states it, is the one directive that covers the rest (decided 2026-10-08): `armonik_transport=debug` alone shows that target alone, `*=off` alone shows nothing, and a stray word shows nothing. An unknown directive is no error; one that is not understood is ignored with a warning the filter does not hide. The rules and the cases are in observability.md. Rejected: text-prefix matching, which makes `h2` mean `h2x`; layering the user's directives over the default's, which leaves `*=off` unable to silence the engine; a fallback to warn for what a filter without a level for every target does not cover, which makes the default's level for every target survive a filter that never mentioned it | T10.1, decided |
| The .NET log queue | **Bounded at 16384 records, the newest dropped and counted** (T10.1). The binding's callback copies each record into the queue and returns; a thread of its own writes it to the `ILoggerFactory`, and says how many were lost before the next record it writes. An unbounded queue would trade a slow provider for the process's memory, and a blocking one for an engine thread, which the callback's contract forbids. 16384 is a burst of debug events from a few channels with a provider stalled for a while - a record is a few hundred bytes, so a few megabytes at most; a provider that cannot keep up with it never will. The queue is flushed at the runtime's disposal and at a refused creation | T10.1, decided |
| The per-call delivery queue on .NET | **Open, and the three objections to `System.Threading.Channels` were wrong.** A bounded `Channel<Slot>` allocates nothing per element that the ring does not, the element being a reference to a native buffer rather than the buffer; a queue that removes the item at the take is no obstacle, because `ak_event_consumed` names the payload it releases, so the engine discharges what comes back rather than what it handed out in order; and level 2's `RingHead`/`RingTail` bind nothing, since that level describes this binding and a refinement needs only a mapping, which may be fictional. What a swap does not touch is the phase machine and the read-versus-token arbiter, which are the actual complexity and have no library answer. What it costs is a package reference on .NET Framework and the release rule: `DeliveryRing.Release()` is the sole releaser of an accepted payload, and a queue that hands the item out cannot hold that invariant - it returns to being the caller's discipline. `DeliveryRing` is one 122-line type, so the swap is mechanical whenever it is wanted | Layer 4 |
| How the C ABI is kept in five places | **Generated from the Rust, and the artefact committed.** `abi.rs`, the header, `NativeMethods.cs`, `tests/layout.rs` and `AbiLayoutTests.cs` are one contract written out five times by hand. `cbindgen` emits the header and `csbindgen` the P/Invoke declarations, verified by the same regenerate-and-compare step `ChannelOptions.g.cs` already has, and the prose the header carries moves into `cbindgen.toml`'s `header` and the Rust doc comments. What does not become redundant is the .NET layout test: `Marshal.SizeOf` and `Marshal.OffsetOf` measure what the CLR does with the declarations, per target framework and per architecture, and a generator proves the declarations match the Rust rather than that the runtime lays them out as Rust does. T3.6, before T4.0 | Layer 3, decided |
| Guarding a buffer or a payload given back twice | **Not built, and if it ever is, behind a feature of its own rather than `cfg(debug_assertions)`.** The `LENT_TAG` in the allocation does not guard this and cannot: it is read from the thing being validated, so a second give-back reads eight bytes of freed memory before any check runs, and no in-allocation scheme fixes that. A guard that works is out of band - a per-call set of live owner pointers, on the lend and the return of every message - and what it would protect is a rule the header already assigns to the host outright, calling a second give-back undefined behaviour rather than a refusal because "there is nothing left to refuse with". The debug build is the wrong home for it twice over: it is the build this repository's own tests run against, so the cost lands on the work rather than on the question, and a guard that exists only where nobody deploys is one no host can ask for when it wants it. A feature flag is the shape - off by default, named, and switched on by whoever is bringing up a host | Layer 3, decided |
| How the binding learns a channel's delivery window | **It reads it back from the engine: `ak_channel_delivery_window(channel, &window, &error)`, once the channel is created** (decided 2026-10-07, T6.8). The window a channel sizes its rings from is settled by the engine from the channel's own document and the runtime's `ChannelDefaults`, and a runtime created from sources states its defaults where the binding cannot see them; the binding sends the document as given and refuses a window past `MaxDeliveryCredits` after the read, closing the channel it just made. Rejected: the binding reading the runtime's sources for the window, a second reading of what the engine loads. Additive, the ABI version staying 1 | Layers 3 and 4 |
| One runtime per process: choice or implementation limit | **A choice, and now requirement 14.9.** Several tokio runtimes in one process share the machine's cores without knowing of each other. `static LIVE` and the three `OnceLock` registries enforce it and the header states it at `ak_runtime_create`; what follows is that the memory ceiling its creator sets is the process's, and a second `NativeRuntime.Create` is refused rather than reconfiguring it | Requirement 14, decided |
| How the engine's threads are laid out | **A thread per channel**, a current-thread tokio runtime that runs the channel's connection and its calls, and a runtime of one worker for the shutdown. A call that stays on one thread pays no wake-up of another: a prototype on the unary benchmark, on .NET 8, was faster at the median in each of three passes against one shared multi-thread runtime, by 26 to 223 us, the low end within the spread between passes. What it costs: a channel's calls share one thread for their CPU work, which nothing yet measures with many calls on one channel; a thread takes about 0.6 ms to start, against 8.5 ms to open a channel over TLS on loopback, and holds a stack and an I/O driver while idle. There is no worker count left to configure, so `worker_threads` leaves `ak_runtime_config` and `WorkerThreads` the runtime's options. A process that opens thousands of channels would want a fixed pool with each channel pinned to one of its threads instead | Requirement 6.7, decided 2026-10-03 |
| The delivery window a channel gets by default | **Four.** With one, the response's message is held until the host has given the head back, a round trip through the host's thread pool between two events that arrive together. On the .NET 8 unary benchmark, in four interleaved passes, two credits took that step from 38-49 us to 12-14 us at the median and the end of a call from 128-150 us to 93-131 us; four, measured in a pass of their own, did as well. | What a rate limit counts, and what a request over it does | **`Grpc.RateLimit` is tower's `RateLimit`, per channel: `Calls` requests start in a window of `PerSeconds`, and a call's first attempt over that waits for the next window rather than failing; a retry the policy chooses does not wait, it is skipped.** A request is an attempt - a call's first, each retry, and a resend of one its peer never processed - because the server sees each as a request, and a limit that left retries out would not bound what reaches it; a streaming call is one request, counted when it starts, and its messages are not limited.
